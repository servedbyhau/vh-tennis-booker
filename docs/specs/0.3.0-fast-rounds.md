# SPEC: 0.3.0 Fast rounds

## Goal
Shorten each booking round to what the app and its server need. The first real 06:00 run
(2026-10-09) booked both slots, but rounds took 11.0 s and 7.1 s. Reading the code against
uiautomator2 showed about 50 device commands per round, most of them repeated lookups:
`wait()` before `click()`, which itself waits again and reads the bounds before tapping.

## Measurements (MuMu, 2026-10-09)
| Command | Median |
|---|---|
| `exists` | 41 ms |
| `info` (bounds of one element) | 60 ms |
| `info_list` with a regex selector | 105-177 ms |
| `dump_hierarchy` (every element of the screen) | 69 ms |
| `window_size` | 125 ms |

App and server time, measured by polling dumps: calendar after "Sân Tennis" 0.14 s, slot
list after tapping the date 2.1 s, court list 1.5-2.0 s, booking details 0.5 s,
confirmation 0.14 s. The slot list overflows a 540x960 screen by 383 px, and slots grow
with the screen height; at 540x1600 all 13 slots fit and the list no longer scrolls.

## Design
1. **One dump per screen.** `screen.Screen` parses a hierarchy dump into nodes (label,
   visible bounds, clickable). Matching (`screen.Match`) happens locally.
2. **Waiting is locating.** `Booker.wait_for(find, timeout)` reads the screen until a finder
   returns something, e.g. the target day; the same result carries the coordinates to tap.
   A step costs one dump per poll plus one tap; polls sleep 20 ms.
3. **Taps by coordinates** from the latest dump (`device.click(x, y)`), never stored across
   screens. Two taps on one screen use one dump: slot then "Tiếp tục".
4. **Entry located ahead.** Two seconds before the start time the runner reads the
   utilities list again (`Booker.locate_entry`); at the start time the first command is the
   tap on "Sân Tennis". The read also wakes the connection after the long wait.
5. **Client-side polling everywhere.** No `wait()`/`wait_gone()` on the device, no fixed
   sleeps except the poll interval.
6. **Scrolling only when needed.** A slot is tapped when its clipped bounds show most of it
   above the sticky button; otherwise the list is swiped and read until it stops moving.
   The screen size comes from the dump, because `window_size()` reported the landscape size
   (960, 540) while MuMu ran the tablet resolution with the app in portrait.
7. **Court check.** A court labelled "Hết chỗ" fails the round with `SlotUnavailableError`.
   The venue screen is still tapped when shown; checking for it costs nothing extra.
8. **Command count** per round is logged at debug level.

## Emulator setup
MuMu instance 0 uses a custom resolution of 540x1600 at 220 DPI:

```
MuMuManager.exe setting -v 0 -k resolution_mode -val custom -k resolution_width.custom -val 540 -k resolution_height.custom -val 1600 -k resolution_dpi.custom -val 220
```

The flow still works at other sizes; it only scrolls more.

## Out of scope
Coordinates calibrated in advance (no faster: each screen must be read to know it has
appeared, and that read already returns the coordinates); several accounts in parallel
(later version); handling a slot taken during the round beyond failing it.

## Verification
- Unit tests drive a scripted fake app through dumps; a full round costs 16 commands.
- Timed dry run on MuMu: round 1 to the accepted terms took 5.9 s (8.7 s with 0.2.0 at the
  same time of day), of which about 4.5 s is app and server time.
- A real 06:00 run books both slots.
