# SPEC: Desktop app

The backend (0.5.0) and the browser UI (0.6.0) are released; the desktop packaging (Tauri,
PyInstaller, installer) is the last step before 1.0.0. This file holds the product decisions the
app follows and the packaging plan. The implementation is in [architecture.md](../architecture.md).

## Goal

A desktop app a resident can install, set up and leave running, without editing files or
reading English logs. The engine stays what it is (it wins the 06:00 race unattended); the app
adds setup, settings, a schedule switch, history and an activity log around it.

## Product decisions

- **Where it runs:** desktop only, on the PC that runs MuMu: a React UI talking to a local
  backend on `127.0.0.1`. Phone access (login, firewall) and a phone layout are not planned; the
  packaged window gets a minimum size instead. The one screen fills the window from 1240 x 640
  (a 1920 x 1080 laptop at 150 % gives about 1280 x 650); its content is at most 1360 wide,
  centred; a smaller window scrolls the page. The ticket and the side panel keep their
  four rounded corners and scroll inside (the ticket its choices, its dry run row staying
  at the foot), with one thin, arrowless scroll bar in the paper's colours.
- **Screens** ("Vé giấy" design; mockups: https://claude.ai/artifact/9U4RU81bLsyEaD9G6Crapr,
  private; one-screen mockup: https://claude.ai/artifact/MneuR5X7eqr9btwQw1hLYY, private):
  one screen, no menu. The header holds the name, the status line and VI/EN. On the left the
  next booking as a ticket that holds the booking settings, the daily switch and the dry run,
  or the live steps of a run; on the right a panel of two tabs, History | Setup. The panel opens
  on Setup while a setup task is left or the dry run and the daily switch are not both done,
  else on History; the Setup tab shows the count of tasks left in red. The old addresses lead
  to the one screen.
- **Settings:** the resident picks from ready-made choices only, on the ticket, and each
  press saves: up to two slots in booking order (the app gives a flat two slots a day; more set
  by hand still show), the subdivision, the sport and the court. The play day is not a choice:
  it is always two days after the next run. The ticket has two parts: above the perforation
  only what is set (the play day and the court on one row, the slots in booking order on the
  next, large, numbered only on the choices below; a line only while the daily switch is off), following each press at once; below
  it the choices.
  The choices wait while a save is on its way and while a booking or a dry run goes on. Everything else (times, app labels, fallback
  points, timeouts) is the developer's, in `config.toml`, as are the slot list
  (`ui/src/booking.ts`) and the subdivisions, sports and courts (`src/court_booker/catalog.py`,
  copied to `ui/src/catalog.json` by `tools/export_openapi.py`).
- **Device setup** (the Setup tab): the user installs MuMu and the Vinhomes app and logs in,
  and ticks each (the app never sees a password and does not check them; the ticks stay in the
  browser's storage). The rest needs no button: every run finds MuMu when the configured
  folder is wrong and sets 540x1600 at 220 DPI on a stopped MuMu before starting it (a running
  one is only logged), and switching the schedule on allows wake timers. A setup task is an
  unticked step. The ticket's tabs on top ("Máy 1", "Máy 2") choose the machine the ticket
  and the Setup tab show; there are always two, the second (MuMu 1) switched off until its
  "Dùng máy này" switch adds its `[[instances]]` table (off removes it, so an older runner
  never meets a key it does not know). The app and the login are ticked for each machine that
  books, MuMu once; a machine switched off is pale and counts no task. While anything is left the tab starts with three lines on how to use the app;
  then they move into its guide (how to use it, every morning and what the PC needs, the usual
  problems). The notification switch sits on the ticket, beside the daily one. Every run
  silently starts MuMu,
  connects ADB, starts the driver, restarts the app and turns off animations and notification
  banners.
- **Schedule:** the "Tự đặt" ("Auto-book") switch on the ticket, allowed once a dry run
  passed; a passed dry run never turns it on by itself, the status line asks for it instead. The status
  line's order: a run going on, setup tasks left, no dry run passed, the switch off, Windows
  blocking wake timers (turning the switch off and on allows them again), ready.
  The PC must sleep, not shut down, stay signed in to Windows, and be plugged in.
- **One run at a time:** the 06:00 run, a dry run, auto setup (`court-booker setup --auto`)
  and command-line runs take the lock; no dry run or auto setup from the wake time to 5 minutes after the start; the 06:00 run
  takes over a holder 2 minutes before the start.
- **History:** every run writes to one SQLite database, whoever started it; the UI only reads.
  Everything is kept. The History lists the runs of ten days at a time, newest first, real
  bookings unless "include dry runs" is ticked, each in two lines: its play day with a short
  weekday and court, and a mark ("2/2", "1/2", "0/2", "THỬ" for a dry run) in the stamp's
  colour; then each slot booked (✓) or not (✕, the reason on hover) and when it started, after
  an icon of how (clock on schedule, person by hand). A run opens in place of the list with
  its full stamp, its slots with their reasons, every step and the technical log.
- **Language and design:** Vietnamese (default) and English, every string in translation files;
  the UI language is kept in browser storage, never in `config.toml`, and VI/EN also gives
  the Windows notification its language. Paper look: warm grey
  ground, paper cards, stamp blue for booked, orange-red for failed; Bricolage Grotesque and IBM
  Plex Mono; light only; every text color at WCAG AA (4.5:1).
- **Never slow a booking:** while a run goes on the UI asks the backend nothing per step; data
  refreshes at run boundaries only.

## Packaging (to do, last before 1.0.0)

Version number set when it starts.

1. PyInstaller build of the backend and engine (one folder, no Python needed). One folder, not
   one `.exe`: a one-file app has a parent process that outlives a kill and unpacks to `%TEMP%`
   on every run, and the task needs a steady path. The resident still gets one installer.
2. Tauri shell with the backend as a child process; window `minWidth` 1280, `minHeight` 720.
   The backend serves the built UI and the window opens `http://127.0.0.1:8765`: one origin, no
   CORS, and browser storage keeps one fixed origin.
3. The schedule runs the installed engine (since 0.19.0).
4. NSIS installer, per user (no admin rights), unsigned: SmartScreen's "Run anyway" is expected.
   The `Tag` workflow pushes the tags with `GITHUB_TOKEN`, which starts no other workflow,
   so it calls the `Desktop` workflow, which builds the installer and publishes the release
   page.
5. Docs and release.

Verified when a clean Windows user installs the app, completes setup, passes a dry run and books
at 06:00 from the installed app.

## Out of scope

Phone access, Telegram setup, installing MuMu or the Vinhomes app, logging in for the user, a
health check before 06:00, fallback slots or courts, counting the monthly quota.
